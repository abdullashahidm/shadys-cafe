## End product
As development drew to a close, I found that I had coded a command-line based interactive Italian-ish café simulator. This program plays jazzy, relaxing music throughout your visit, creating a dreamy atmosphere that makes you want to sit back. It utilizes ASCII artwork to paint pictures of the scenes as you progress through your trip to this café. It allows you to view a menu and order items. It has an intelligent, logic-based ordering system that can detect and remove not-on-menu items, detect how many numerical quantities of item you've ordered, such as "2 pizzas", and can also detect if you've made spelling errors in your order and adjusts accordingly. For instance, if you mistakenly typed "Lasania", the program uses fuzzy matching via Rapidfuzz to understand that what you meant to say was "Lasagna" and thus autocorrects your request to that, instead of inflexibly spitting out an error. \(That's also the feature I'm most proud of!\) It uses your order to also generate you a custom slip, which it prints on screen.

For the Rapidfuzz usage, I briefly contemplated against it as well. I considered using an API call to a free LLM, such as Gemini 2.5. In that call, I'd hardcode a prompt containing the menu, concatenate the user's order to the prompt and ask Gemini to remove not-on-menu items and to autocorrect misspellings, but I ultimately decided against it because I wanted my simulation to not be like a thin client in that regard and to handle it's own processing. It's a decision I'm glad I stuck with, because it makes simple logic seem magical!

## The nightmare that was testing
Perhaps the most difficult part of this entire project was writing code to automatically test it. See, I had coded the entire program so happily, and in my excitement at how well it was turning out, I neglected to consider how I might test this program, that was, in essence, so heavily reliant on user input. The issue hit me like a jab to the face as I finally sat down to write the testing. _Wait a moment... how exactly do I test it, now?_ The answer was simple enough to understand. Having decided between unittest and pytest that I would use pytest, I knew that I had to mock the user inputs so when pytest ran the tests it was feeding my code a predetermined set of inputs to whom I as the developer would know the answer to and hence produce the expected results of and check for them. But it was easier said than done. I had to sit through multiple tutorials on pytest and monkeypatch and other relevant concepts, but ultimately, I'm really pleased I did, because I figured out how to write the tests. I was so incredibly relieved when I began seeing those green checkmarks! After the tests had been written, splitting them into seperate files, one for each module was simple enough.

## New things learned
Completing Harvard CS50P is most definitely going to be a bragging point for me. How many people in the world can say they've completed a Harvard level programming course? However, there were a few features in this program that I needed to implement that I wouldn't have learned had I applied just my learnings from the course only. For starters, the backbone of the experience, the sound system. I knew I wanted to create a relaxing, laid back jazz sort of environment in my café, but I wasn't entirely sure how I'd do that. A few quick searches later, from the choices of playsound and pygame, I had opted for pygame. [This](https://www.youtube.com/watch?v=xdkY6yhEccA) video tutorial helped me learn most of the logic I applied to coding the sound system. 

As I wrote and tested the sound code, I was delighted to see it work really well, but the key issue that arised was that I was experiencing the effects of blocking. Essentially, I had coded the system in a way that when one audio track was playing, the system would check if it were finished or not and if not, it would time.sleep for a second before re-checking. While I think this was a good move to make sure the next track plays as fast as can be after the first finishes, using time.sleep makes the entire code pause for a second. It wasn't too noticeable during usage, but I am someone who's a little detail-obsessed, so the small jittery pauses caught my attention. I went poking around online, and though it took a pretty long time, someone on Reddit suggested [threading](https://www.reddit.com/r/learnpython/comments/1nttnxg/how_can_i_make_a_function_pause_without_pausing/). Thus followed another few tutorials on the understanding and usage of threading but ultimately I was able to solve the issue and run my code continously without having to time.sleep the main logic as well. 

Some other modules I learned about were Rapidfuzz and much more depth on unit testing with pytest. I also learned to consider how to test programs and modules before actually coding them, so they can be designed and written in a test-friendly manner.

I also learned a lot about Pythonic ways to write code which quite interested me. Things like a global constant being IN_ALL_CAPS for ease of other programmers reading it, and \_\(s\) in front of a function name denoting it as being private.
